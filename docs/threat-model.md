# Threat model

Scoped to the platform code on `main` (`src/platform/*`, root `package.json`, `.agents/skills/*`). Apps under `src/apps/` are empty today; rows describe the shared platform mechanisms every app inherits.

| Threat | What the prototype does today | What a production pilot would add |
| --- | --- | --- |
| A user acting above their role | `authorize(actor, action, resource)` in `src/platform/authz/index.ts` scans every manifest's `policies["<app>.<action>"]`; an unmatched key throws `ForbiddenError`, and `actor.role === "admin"` returns early past every policy. Policies are plain in-manifest functions. | Resource-scoped policies enforced server-side per row, narrowing/removing the blanket `admin` bypass, and negative tests per policy; today `admin` passing every known policy is an all-or-nothing escalation surface. |
| Two users editing the same record | `optimisticUpdate` in `src/platform/db/index.ts` updates `WHERE id AND version` and bumps `version`; `res.changes === 0` throws `ConflictError` (409). `version` rides as a hidden form field per the mutation rule. | Same guard, but it only protects tables that actually carry an integer `version`; a pilot would enforce the column across all mutable tables and surface a merge/reload UX rather than a bare 409 string. |
| Audit rows altered by an app bug | Append-only: `append` in `src/platform/audit/index.ts` only inserts, and "no code path updates or deletes `audit_log`" is enforced only by convention/manual review (spec criterion 12). `withMutation` in `src/platform/db/index.ts` wraps the entity write and `audit.append` in one transaction so a throwing `fn` rolls back both. | DB-level protection so a stray `update`/`delete` can't compile or run (triggers, revoked grants, or a WORM store), plus a lint rule blocking writes to `auditLog` outside `append`, since today it's guarded only by discipline. |
| Audit rows altered by someone with direct DB access | Detection only: `hashRow`/`verify` in `src/platform/audit/index.ts` chain each row via `prev_hash`; `verify` recomputes and returns `{ ok: false, brokenSeq }`, exposed as `audit:verify` (`BROKEN at seq <n>`) and the `/admin/audit` "Verify chain" button. The SQLite file `./data/app.db` (`src/platform/db/index.ts`) is a plain writable file. | Tamper-evidence that's externally anchored (periodic hash export/notarization to WORM or a separate append-only store) and scheduled verification/alerting, since the local chain can be fully recomputed by anyone who can rewrite the file. |
| The coding agent reaching real data or secrets | `getKycProvider`/`getPaymentsProvider` in `src/platform/adapters/index.ts` return deterministic fakes and throw `"not implemented"` when `*_PROVIDER=real`; there are no real credentials to reach. `.agents/skills/new-internal-tool/SKILL.md` instructs the agent to never touch the platform, generated registry, other apps, or audit rows. | A sandboxed agent runtime with scoped, short-lived credentials and a secrets manager, plus mechanical enforcement of the "never touch" list; today the boundary is prose in the skill file and the fact that no real providers exist. |
| Denied actions leaving no trace | `authorize` throws `ForbiddenError` before `withMutation` runs, and audit rows are only written inside `withMutation`/`append`; there is no `console`/log call on the deny path in `src/platform/authz/index.ts`. `runAction` maps the error to `{ ok: false, code, message }` and returns. | A separate security/attempt log (allowed and denied) so 403s are recorded; today a forbidden action produces a 403 response and zero durable evidence. |
| Dependency drift across many apps | A single root `package.json` is the only manifest in the repo; all future `src/apps/*` share one dependency tree and lockfile. `docs/sessions/platform.md` notes `npm audit` already reports 6 vulns (5 moderate, 1 high) left as-is, and CI runs Semgrep `p/default` but no SCA. | Automated dependency scanning/updates (Dependabot/Renewal) and an SCA gate in CI; a per-app dependency policy is moot because there is one shared tree, so drift is really "the whole platform on one version set." |
| SSO cutover from the dev login | `buildProviders` in `src/platform/auth/providers.ts` always registers the `Credentials` provider (bcrypt against seeded `*@demo.local` users) and only *adds* the `oidc` provider when `AUTH_OIDC_ISSUER` is set — Credentials is never turned off. | An environment switch that disables the Credentials provider in production so demo passwords can't authenticate once OIDC is live; today enabling SSO leaves the dev login active alongside it. |
| The dev auth secret fallback | `src/platform/auth/config.ts` sets `secret: process.env.AUTH_SECRET ?? "dev-only-insecure-secret"`, signing the 8h JWT sessions; the comment notes it's for zero-setup dev/e2e/CI. | Fail-fast startup when `AUTH_SECRET` is unset in production so JWTs can't be forged with a public constant, plus secret rotation; today an unset env silently signs sessions with a known string. |
