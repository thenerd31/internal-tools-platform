# Threat model

Scoped to the platform code on `main` (`src/platform/*`, root `package.json`, `.agents/skills/*`). The first table describes the shared platform mechanisms every app inherits; the "App rows" table at the end covers the KYC and refunds apps.

| Threat | What the prototype does today | What a production pilot would add |
| --- | --- | --- |
| A user acting above their role | `authorize(actor, action, resource)` in `src/platform/authz/index.ts` scans every manifest's `policies["<app>.<action>"]`; an unmatched key throws `ForbiddenError`, and `actor.role === "admin"` returns early past every policy. Policies are plain in-manifest functions. | Resource-scoped policies enforced server-side per row, narrowing/removing the blanket `admin` bypass, and negative tests per policy; today `admin` passing every known policy is an all-or-nothing escalation surface. |
| Two users editing the same record | `optimisticUpdate` in `src/platform/db/index.ts` updates `WHERE id AND version` and bumps `version`; `res.changes === 0` throws `ConflictError` (409). `version` rides as a hidden form field per the mutation rule. | Same guard, but it only protects tables that actually carry an integer `version`; a pilot would enforce the column across all mutable tables and surface a merge/reload UX rather than a bare 409 string. |
| Audit rows altered by an app bug | Append-only: `append` in `src/platform/audit/index.ts` only inserts, and "no code path updates or deletes `audit_log`" is enforced only by convention/manual review (spec criterion 12). `withMutation` in `src/platform/db/index.ts` wraps the entity write and `audit.append` in one transaction so a throwing `fn` rolls back both. | DB-level protection so a stray `update`/`delete` can't compile or run (triggers, revoked grants, or a WORM store), plus a lint rule blocking writes to `auditLog` outside `append`, since today it's guarded only by discipline. |
| Audit rows altered by someone with direct DB access | Detection only: `hashRow`/`verify` in `src/platform/audit/index.ts` chain each row via `prev_hash`; `verify` recomputes and returns `{ ok: false, brokenSeq }`, exposed as `audit:verify` (`BROKEN at seq <n>`) and the `/admin/audit` "Verify chain" button. The SQLite file `./data/app.db` (`src/platform/db/index.ts`) is a plain writable file. | Tamper-evidence that's externally anchored (periodic hash export/notarization to WORM or a separate append-only store) and scheduled verification/alerting, since the local chain can be fully recomputed by anyone who can rewrite the file. |
| The coding agent reaching real data or secrets | `getKycProvider`/`getPaymentsProvider` in `src/platform/adapters/index.ts` return deterministic fakes and throw `"not implemented"` when `*_PROVIDER=real`; there are no real credentials to reach. `.agents/skills/new-internal-tool/SKILL.md` instructs the agent to never touch the platform, generated registry, other apps, or audit rows. | A sandboxed agent runtime with scoped, short-lived credentials and a secrets manager, plus mechanical enforcement of the "never touch" list; today the boundary is prose in the skill file and the fact that no real providers exist. |
| Denied actions leaving no trace | `authorize` throws `ForbiddenError` before `withMutation` runs, and audit rows are only written inside `withMutation`/`append`; there is no `console`/log call on the deny path in `src/platform/authz/index.ts`. `runAction` maps the error to `{ ok: false, code, message }` and returns. | A separate security/attempt log (allowed and denied) so 403s are recorded; today a forbidden action produces a 403 response and zero durable evidence. |
| Dependency drift across many apps | A single root `package.json` is the only manifest in the repo; all future `src/apps/*` share one dependency tree and lockfile. `docs/sessions/platform.md` notes `npm audit` already reports 6 vulns (5 moderate, 1 high) left as-is, and CI runs Semgrep `p/default` but no SCA. | Automated dependency scanning/updates (Dependabot/Renewal) and an SCA gate in CI; a per-app dependency policy is moot because there is one shared tree, so drift is really "the whole platform on one version set." |
| SSO cutover from the dev login (fixed in PR #4, found via this threat model) | `buildProviders` in `src/platform/auth/providers.ts` omits the `Credentials` provider when `NODE_ENV=production` unless `AUTH_ALLOW_DEV_LOGIN=true`; the `oidc` provider is still added whenever `AUTH_OIDC_ISSUER` is set. Previously, Credentials was always registered — demo passwords stayed live alongside OIDC. | Secret rotation and eventually removing `AUTH_ALLOW_DEV_LOGIN` once the escape hatch is no longer needed. |
| The dev auth secret fallback (fixed in PR #4, found via this threat model) | `resolveSecret()` in `src/platform/auth/config.ts` throws `AUTH_SECRET is required when NODE_ENV=production` at startup instead of falling back to the dev constant; dev/test keep the zero-setup fallback. Previously, `secret` silently fell back to `"dev-only-insecure-secret"` in every environment, so an unset env signed the 8h JWT sessions with a public constant. | Secret rotation, plus a linter/CI check that no env reads `AUTH_SECRET` without the `resolveSecret` wrapper. |

## App rows

Added after the KYC (PR #3) and refunds (PR #5) apps landed. Same columns; each row names the function that enforces it and the test that covers it.

| Threat | What the prototype does today | What a production pilot would add |
| --- | --- | --- |
| An analyst reading another analyst's case | `getCaseFor` and `getCaseHistory` in `src/apps/kyc/service.ts` load the row, then call `authorize(actor, "kyc.case.view", kase)`; the `kyc.case.view` policy in `src/apps/kyc/manifest.ts` lets an analyst see a case only if `assigneeId` is theirs or `null`. `listCasesFor` applies the same filter in SQL, so the queue never lists another analyst's case. The detail page maps `ForbiddenError` from either read to the 403 page. Tests: `kyc.test.ts` AC11 ("analysts see own and unassigned cases, but not another assignee's") and "returns null for missing cases and rejects inaccessible cases"; `e2e/kyc.spec.ts` checks the hidden case and the direct-URL 403. | Row-level filtering enforced by the database (views or RLS) rather than repeated in two service functions, and an attempt log for denied reads — today a denied read is a 403 with no durable trace. |
| An analyst deciding above the risk threshold | `decideCaseAs` in `src/apps/kyc/service.ts` calls `authorize(actor, "kyc.case.decide", kase)` before validating or writing; the policy in `manifest.ts` requires `riskScore < 70` and `assigneeId === actor.id` for analysts and only `supervisor` (or `admin`) otherwise. `claimCaseAs`/`claimNextAs` apply the same threshold on claim, so a high-risk case is never assigned to an analyst by the app. The UI disables the form via `decideDisabledReason`, but that is display only — the server check is the gate. Tests: `kyc.test.ts` AC3 ("analyst cannot decide an own high-risk case", asserts no audit row), AC1 (claimNext skips the 80), AC4 (disabled reason), AC5 (supervisor can). | The threshold as data (config or table) rather than the literal `70` in the manifest and `SUPERVISOR_THRESHOLD` in `schema.ts`, plus a denied-attempt log; policies are booleans, so a denial cannot say which rule failed. |
| A refund approved by its requester, or issued twice | Self-approval: `approveRefundAs` in `src/apps/refunds/service.ts` calls `authorize(actor, "refunds.refund.approve", refund)`; the policy in `src/apps/refunds/manifest.ts` is `role === "lead" && refund.requestedBy !== actor.id` (admin bypasses, per the platform rule). Double issue: `requestRefundAs` returns the existing row for a repeated `idempotencyKey`; `approveRefundAs` checks `version` (409) and `status === "pending_approval"` (422) before `withMutation`, re-checks both inside the transaction, and `issueWithin` bumps the status with `optimisticUpdate` before calling `PaymentsProvider.refund` with the same `idempotencyKey`, so the fake provider returns the same `providerRef` for a retry. Tests: `refunds.test.ts` AC4 ("requester cannot approve own refund; another lead can"), AC5 (repeated idempotency key), AC9 (second approver with stale version gets `ConflictError`), AC11 (terminal refunds reject further transitions), "approval re-validates against remaining balance". | Approval as a distinct role from request (separate accounts, not just a `requestedBy` check), a real payments provider whose idempotency is server-side and durable across restarts (the fake's map is in-memory), and reconciliation against provider records; today "issued twice" is prevented by the app's own state machine only. |
